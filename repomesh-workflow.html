RepoMesh 工作流程

从左到右展示一次跨仓库场景交付：先由 harness 选择并校验 scenario，再把 task 作为恢复点，经过计划与评审闸门后，按场景顺序进入业务仓库执行、验证并记录完成状态。

必需/通过 可选/注意 停止/阻塞 记录/上下文
1 入口识别
确定 scenario
用户显式命名时直接使用；否则只读扫描 scenarios/* 找匹配。
多个候选或无匹配时先询问，不创建 task、不进入业务 repo。
必读顺序
AGENTS.md 定义全局协议和 YAML 语义。
scenario.yaml 定义 repo、顺序、依赖、检查。
README.md 定义 SOP、风险和完成标准。
2 模板校验
机械验证
运行 bin/repomesh validate-scenario。
错误时停止；恢复任务则记录 scenario_invalid。
执行摘要
plan-scenario 汇总 repo 顺序、路径、输出、依赖、指令、关键文件和 checks。
YAML 结构由 scenario.yaml 权威定义。
3 Task 记忆
恢复点推荐复用模式
init-task 创建 spec.md、status.md、decisions.md、validation.md。
继续任务时先读四个 task 文件，再重新校验 scenario。
任务特定状态
expected branch 只存在 task 文件，不写进 scenario。
所有 gate、blocker、验证结果都即时落盘。
4 计划闸门
Preflight
preflight 检查分支、dirty state、缺失指令和关键文件。
分支不匹配时停止，不自动 checkout 或创建分支。
Planning Pass
按 repo 顺序读取本地指令和 key files，识别合同、风险、下游影响。
更新 spec、dependency readiness、Planning Gate。
Spec Review Gate 需用户批准或明确跳过后才实现。
5 仓库执行循环
按场景顺序进入
再次运行 git status 并精确匹配 expected branch。
检查 upstream dependency readiness 后再改下游 repo。
实现与验证
设置 implementing:<repo>，补充 repo-local notes 后修改代码。
设置 validating:<repo>，运行 scenario 声明 checks。
检查失败默认 blocked；用户接受失败才可继续。
6 完成/恢复
完成条件
所有 repo 完成或有跳过理由；checks 通过、跳过或失败接受已记录。
outputs、depends_on、风险和完成标准写入 task 文件。
中断安全
status.md 保存 current step、repo 表、gate、依赖 readiness 和历史。
恢复时从 task 文件和最新 scenario 结构继续，不依赖对话记忆。
1场景层负责结构

harness 只声明跨 repo 的参与者、顺序、依赖、关键入口和检查，不替代业务 repo 的本地规则。

scenario.yaml
order -> repos -> outputs
depends_on -> checks
2Task 层负责恢复

每次具体交付都把分支、计划、阻塞、验证和决策写入 task 目录，保证可中断、可恢复。

tasks/<task>/
spec.md status.md
decisions.md validation.md
3业务 repo 保持独立

每个 repo 独立检查 git 状态、分支、本地指令和测试结果；不混合提交，不自动执行破坏性操作。

repo entry:
read instructions
inspect key files
implement -> checks
